# 버티컬 에이전트와 도메인 깊이

## 핵심 요약

버티컬 에이전트의 경쟁 축은 모델 성능 벤치마크가 아닌 **도메인 깊이 × 거버넌스 설계**다. 채널코퍼레이션 알프의 월 100만 건 80% 해결률은 GPT-4o가 아닌 11년치 CS 데이터와 룰 가드레일이 만든 결과다. 도메인 요구사항이 아키텍처를 결정한다. 모델이 아키텍처를 결정하는 게 아니다.

## 상세 내용

### 레퍼런스 사례: 채널코퍼레이션 알프 (raw 원문 기준)

- 월 100만 건 고객 상담 처리, **80% 사람 개입 없이 해결**
- 경쟁력의 핵심: GPT-4o가 아닌 2013년부터 11년간 축적한 B2B SaaS 고객 상담 데이터 + 룰 베이스 가드레일
- 오늘 시작하는 팀이 이 데이터를 따라잡으려면 최소 2~3년 필요

### 범용 모델 성능 격차의 현실 (raw 원문 기준)

MMLU, HumanEval, 주요 추론 벤치마크에서 GPT-4o와 Claude Sonnet의 점수 차이는 수 퍼센트 이내. 이 차이가 프로덕션에서 80% 해결률과 40% 해결률의 차이를 만들지 않는다. 범용 모델 경쟁은 이미 상품화 단계에 진입 중.

### 도메인 깊이의 3가지 구성 요소 (raw 원문 기준)

**1. 도메인 언어 체계**

범용 LLM은 "채널톡 블럭 설정", "티켓 에스컬레이션 조건", "API 웹훅 연동 오류" 같은 맥락을 처음부터 모른다. 수년간의 실제 상담 로그 없이는 어떤 모델도 고객 질문을 맥락 없이 처리 → 잘못된 답변 → 낮은 해결률 → 이탈.

**2. 실패 패턴 데이터**

고객이 어떤 방식으로 오해하는지, 어떤 질문이 반복되는지, 어느 시점에 사람이 개입해야 해결되는지 — 실운영 데이터 없이 설계 불가.

**3. 워크플로우 통합**

에이전트가 티켓 시스템, CRM, 내부 플레이북과 실시간 연결되어야 한다. 이 연결이 없으면 에이전트는 "답변 생성기"에 머문다.

모델만 바꾸는 것 = 엔진만 바꾸고 연료와 도로는 그대로 두는 것.

### 거버넌스 설계 — 신뢰가 진입장벽 (raw 원문 기준)

알프의 룰 베이스 가드레일 예시:
- 법무 관련 질문 → 사람에게 에스컬레이션
- 계약 해지 요청 → 특정 팀으로 라우팅
- 민감 정보가 포함된 응답 → 자동 검수 후 발송

100% 자동화를 목표로 설계하는 것보다, **80%를 자동화하고 나머지를 안전하게 처리하는 쪽이 고객 신뢰를 만든다**.

**Anthropic의 금융 에이전트 패키지 (raw 원문 기준)**: "범용 모델 + 금융 도메인 패키지"가 필요했다는 것은 모델 단독으로는 금융 버티컬에서 충분하지 않다는 것을 Anthropic 스스로 인정한 것.

### 한국 버티컬 신호 3곳 (raw 원문 기준)

| 사례 | 도메인 | 핵심 설계 결정 |
|------|--------|---------------|
| 마키나락스 × 국방과학연구소 | 국방 (14.6억 원 수주) | 자사 AI OS "런웨이" 위에서 에이전트 작동 |
| 인텔리빅스 × 모빌린트 VIXA | 국방·공공 안전 | 클라우드 LLM 없이 온프레미스 NPU — 거버넌스 요구사항이 아키텍처를 결정 |
| OncoAgent Zero-PHI | 의료 | LangGraph 기반, 환자 데이터 외부 미전송, AMD MI300X 온프레미스 |

세 곳에서 같은 결론: **도메인 요구사항이 아키텍처를 결정한다. 모델이 아키텍처를 결정하는 게 아니다.**

### PM이 해야 할 3가지 질문 (raw 원문 기준)

1. **우리 도메인에서 데이터가 가장 풍부한 레이어는 어디인가?** — 가장 많이 축적된 도메인 데이터가 있는 레이어에 에이전트를 먼저 붙인다. 데이터 없는 곳에 에이전트를 붙이면 범용 모델의 한계를 고스란히 받는다.

2. **에이전트가 틀렸을 때 어떤 일이 벌어지는가?** — 실패 비용이 높을수록 가드레일 설계가 복잡해진다. 실패 비용을 먼저 계산하고 가드레일의 범위와 깊이를 결정한다.

3. **인간 검토 루프를 어디에 둘 것인가?** — 인간 개입 데이터가 곧 에이전트 훈련 데이터. 인간 루프를 데이터 수집 채널로 설계하는 팀이 더 빠르게 개선된다.

### 다음 경쟁의 위치

범용 모델 경쟁 → 상품화 단계 진입 중. 다음 경쟁: **도메인 데이터 + 워크플로우 통합 + 거버넌스 설계**. 이것은 모델 회사가 대신 해줄 수 없다.

버티컬 에이전트 PM의 역할: "어떤 모델 API를 쓸까" → "어떤 도메인 레이어를 먼저 잠글까"

### 2026-05-16 보강: 도메인 번들 SKU

Anthropic 금융 에이전트 10종, Claude for Small Business, ServiceNow K26, 달파 300기업 사례는 같은 방향을 가리킨다. 에이전트 비즈니스의 경쟁 단위는 더 좋은 모델이 아니라 **도메인 번들**이다.

도메인 번들은 기능 카탈로그가 아니다. 세 조건이 동시에 필요하다.

1. **워크플로 통합**: 피치북 분석 → 재무제표 해설 → 신용 메모 작성처럼 결과가 다음 단계 입력이 된다.
2. **작업 표면 통합**: Excel·PowerPoint·Word·Outlook 등 사용자가 이미 일하는 표면 안에 들어간다.
3. **권한 게이트**: QuickBooks·PayPal·HubSpot 같은 외부 서비스 접근 전 사용자 승인 구조를 둔다.

한국 시장에서는 달파의 커머스, LGU+×웰컴저축은행×EXAONE의 금융 버티컬처럼 단독 패키징보다 역할 기반 3자 결합이 현실적인 번들 설계 방식이 될 수 있다.

### 2026-05-23 보강: 소버린/엣지 AI와 Where-to-Run

VIXA, 국방·공공 안전, 의료 Zero-PHI 사례는 버티컬 에이전트 설계에 네 번째 질문을 추가한다. **이 에이전트는 어디서 실행되어야 하는가?**

클라우드 에이전트가 못 들어오는 환경은 단순 보수성이 아니라 데이터 주권, 네트워크 단절, 지연, 물리 현장 안전 문제를 가진다. 이 경우 모델 성능보다 온프레미스 NPU, 엣지 배포, 로컬 로그 보존, 현장 운영자의 승인 루프가 아키텍처를 결정한다.

PM의 설계 변수는 다음처럼 갈린다.

- 데이터 외부 반출 가능 → 클라우드 LLM + API orchestration
- 민감 데이터/현장 판단 필요 → 온프레미스 또는 엣지 inference
- 지연이 안전과 직결 → 로컬 모델 우선, 클라우드는 후처리/학습 보조

한국의 국방·공공·의료 사례는 소버린 AI가 정책 구호가 아니라 에이전트 실행 위치를 바꾸는 제품 요구사항임을 보여준다.

### 2026-05-26 보강: 도메인 신뢰와 반복 성과

에이전트가 운영 매출로 전환되려면 **도메인 신뢰**와 **측정 가능한 성과**가 동시에 필요하다. 채널코퍼레이션 알프의 월 100만 건 처리·80% 해결률은 모델 일반 성능보다 11년치 도메인 데이터와 룰 기반 가드레일의 결과다.

반복 예산을 얻는 조직은 월별 KPI를 먼저 설계한다. Virgin Atlantic의 P1 사고 0건, Datadog AI 관측 ARR 성장, NC AI 비용 절감 같은 숫자는 "AI를 썼다"가 아니라 "운영 성과가 반복 측정된다"는 증거다.

따라서 버티컬 에이전트 설계는 도메인 번들 SKU에서 끝나지 않는다. 그 번들이 어떤 반복 KPI를 만들고, 어떤 실패를 안전하게 에스컬레이션하며, 어떤 월별 보고 언어로 예산 갱신을 통과할지까지 포함한다.

### 2026-05-31 보강: Mom and Pop Tech와 지루한 니치

Product Talk의 Mom and Pop Tech 프레임은 AI가 버티컬 에이전트 시장을 아래쪽으로도 넓힌다는 신호다. 과거에는 프로덕션 품질 소프트웨어 구축 비용 때문에 작은 커뮤니티용 도구가 사업성이 없었지만, Claude 같은 에이전트가 인증, 저장, 폼, 간단한 워크플로우를 빠르게 만들 수 있게 되면 개인·소규모 팀이 좁은 문제를 직접 해결할 수 있다.

Starter Story의 "Boring Niche = $1M/Year"도 같은 방향이다. 화려한 범용 아이디어보다 간과된 카테고리에서 이미 작동하는 수요를 자기 방식으로 복제·개선하는 쪽이 더 실용적일 수 있다. 에이전트 비즈니스 관점에서는 대기업용 horizontal agent보다 작은 도메인의 반복 업무, 분명한 지불 의사, 낮은 경쟁 밀도를 먼저 보는 전략이 합리적이다.

### 2026-06-01 보강: 운영 데이터와 workflow surface

Rize v3.0.7 raw는 시간 추적 제품이 Slack Agent, in-app MCP Chat, profitability/events tools로 확장되는 신호다. 버티컬 에이전트는 별도 챗봇이 아니라 사용자가 이미 일하는 Slack, 리포트, 프로젝트 수익성 화면 안으로 들어갈 때 반복 사용된다. 중요한 것은 모델보다 같은 데이터, 같은 권한, 같은 업무 표면을 유지하는 것이다.

Roko's Bas raw의 데이터 희소성 논의도 같은 방향이다. 공개 훈련 데이터가 고갈되고 합성 데이터가 model collapse 위험을 만들수록, 기업의 proprietary operational data가 해자가 된다. 버티컬 에이전트의 도메인 깊이는 단순 지식 베이스가 아니라 실제 클릭, 시간, 티켓, 회의, 승인, 실패 로그 같은 운영 데이터에서 생긴다.

a16z 드론 군집 raw는 physical AI에서도 같은 패턴을 보여준다. 자율 플랫폼을 만드는 것보다 현장에서 계속 작동하게 하는 유지보수·보급 데이터와 운영 루프가 병목이다. 따라서 버티컬 에이전트의 "도메인 깊이"는 소프트웨어 SaaS뿐 아니라 [physical-ai-world-model](/concepts/physical-ai-world-model.md)의 현장 운영 체계에도 적용된다.
